# 支付、登录、推送与定时任务方案

> 状态：定稿  
> 日期：2026-09-11  
> 适用范围：`senior-post-api`、`senior-post-flutter`、`senior-post-manage`

## 1. 定稿结论

1. App 内数字商品和订阅使用 **Google Play Billing**，不使用 Google Pay。
2. 首期只实现 Google Play Billing，支付领域和数据结构预留 Apple App Store In-App Purchase 接入能力。
3. 系统不提供主动退款功能，只处理用户在 Google Play、Apple App Store 等渠道主动申请后产生的退款、撤销和拒付事件。
4. Google 登录使用现有 **Google ID Token + Java 服务端校验 + 自有 JWT** 方案，本期不引入 Supabase Auth。
5. 消息推送使用 Google FCM，不推送任何支付或订阅类消息。
6. 普通信件有两个独立推送时机：匹配成功并进入在途时推送一次，信件真正到达时再推送一次。
7. 所有 Spring `@Scheduled` 入口集中在一个类中，具体任务逻辑委托给独立 Job/Service。

## 2. 通用支付与订阅

### 2.1 目标

建立一套与渠道无关的商品、购买、交易、订阅和权益模型。Google Play 和未来的 Apple App Store 只负责提供渠道事实，业务功能统一根据权益服务判断。

首期范围：

- Google Play 一次性商品和自动续期订阅的通用数据模型。
- Flutter 购买、恢复购买和服务端真实校验。
- Google Play Real-time Developer Notifications（RTDN）。
- 订阅续期、取消续期、宽限期、扣款失败、暂停、恢复、过期、退款、撤销和拒付。
- 管理后台商品管理和只读购买记录。

不在首期范围：

- 后台主动退款、撤销订阅或人工改变支付状态。
- Apple App Store 真实接入。
- 支付、续费、退款或订阅变化的 FCM 推送。

### 2.2 渠道抽象

定义统一接口 `BillingProvider`：

```text
BillingProvider
├── GooglePlayBillingProvider
└── AppleAppStoreBillingProvider  // 未来实现
```

通用能力包括：

- `verifyPurchase`：校验购买并返回渠道状态。
- `getSubscription`：查询订阅最新状态。
- `acknowledgePurchase`：确认首次购买。
- `parseNotification`：解析渠道服务端通知。
- `restorePurchases`：校验并恢复已购权益。

渠道校验、客户端恢复和回调事件最终都必须进入同一个幂等入口：

```text
syncPurchase(provider, purchaseToken)
```

### 2.3 数据结构

#### 2.3.1 `bu_commerce_product`

复用现有商品表，补充或明确：

- `product_code`：稳定的内部商品编码。
- `product_type`：`one_time | subscription`。
- `entitlement_code`：购买后授予的权益编码。
- `title_key` / `description_key`。
- `status` / `sort_order` / `metadata_json`。

本地价格只可作为参考或快照，不得作为真实扣款价格。客户端展示价格以应用商店返回的本地化价格为准。

#### 2.3.2 `bu_commerce_product_channel`

用于内部商品与应用商店商品的映射：

- `product_id`
- `provider`：`google_play | apple_app_store`
- `store_product_id`
- `base_plan_id`
- `offer_id`
- `app_id_or_package_name`
- `environment`：`sandbox | production`
- `status`
- `provider_config_json`

#### 2.3.3 `bu_payment_purchase`

记录一次稳定的购买关系：

- 内部购买号、用户、商品和渠道。
- 外部购买标识。
- Purchase Token 密文及用于唯一索引的哈希。
- `pending | purchased | canceled | refunded | revoked`。
- 购买时间、支付时间、环境和最近渠道快照。

Purchase Token 需要在后续查询渠道 API 时使用，因此应加密保存，日志和后台必须脱敏。

#### 2.3.4 `bu_payment_transaction`

记录资金维度的每次变化：

- `initial_purchase`
- `renewal`
- `refund`
- `chargeback`
- `revocation`

自动续期每次扣款形成独立流水，不能只覆盖首次购买记录。

#### 2.3.5 `bu_subscription`

订阅状态统一为：

- `pending`
- `active`
- `grace_period`
- `on_hold`
- `paused`
- `canceled`
- `expired`
- `revoked`

同时记录当前周期开始/结束时间、是否自动续期、当前 Purchase Token、`linked_purchase_token`、取消原因和最后渠道同步时间。

现有 `bu_vip_subscription` 在迁移期可保留兼容，新的渠道状态以 `bu_subscription` 为真相来源，待业务全部切换后再停用旧表。

#### 2.3.6 `bu_user_entitlement`

复用现有权益表，补充权益编码、来源购买/订阅、生效时间、失效时间、撤销时间和状态。

`bu_user.is_vip` 只能作为性能快照，不能作为支付或订阅真相来源。

#### 2.3.7 `bu_payment_webhook_event`

保存 Google/Apple 服务端通知：

- `provider`
- `event_id_or_message_id`
- 事件类型
- 原始 Payload
- 处理状态
- 重试次数
- 错误信息
- 接收和处理时间

对 `provider + event_id_or_message_id` 建立唯一约束，保证重复通知不会重复发放或收回权益。

### 2.4 Google Play 购买流程

1. Flutter 从 Google Play 查询商品和本地化价格。
2. 发起购买，并设置与当前本地用户关联的混淆账号标识。
3. 客户端将 `productId + purchaseToken + packageName` 传给服务端。
4. 服务端调用 Google Play Developer API 校验购买。
5. 校验包名、商品、环境、购买状态和用户归属。
6. `PENDING` 只落库，不发放权益。
7. 渠道确认购买完成后，事务内更新购买、交易、订阅和权益。
8. 服务端完成 acknowledge，续费事件不重复 acknowledge。
9. 返回最新权益快照给客户端。

同一 Purchase Token 不允许绑定到不同本地用户。

### 2.5 回调、续期与用户退款

Google Play 使用 Cloud Pub/Sub 推送 RTDN。通知只代表渠道状态发生变化，服务端收到后必须再查询 Google Play Developer API，不能直接根据回调文案改权益。

处理流程：

1. 验证 Pub/Sub Push 请求身份和 audience。
2. 解码通知。
3. 按 `messageId` 幂等写入 `bu_payment_webhook_event`。
4. 落库成功后尽快返回 2xx。
5. 后台任务调用 Google API 获取最新状态。
6. 更新购买、交易和订阅，然后重新计算权益。
7. 失败事件进入统一重试任务。

权益规则：

- `active`：保留权益。
- `grace_period`：保留权益。
- `canceled`：只表示关闭自动续期，当前周期结束前保留权益。
- `on_hold | expired | revoked`：停止权益。
- 用户在渠道申请的退款、撤销和拒付：写入交易流水，并按渠道返回的生效时间收回权益。

后台不设置主动退款 API 或按钮，也不允许管理员手动把已支付状态改为已退款。

### 2.6 管理后台

商品管理在现有页面上扩展：

- 内部商品编码、类型、权益和上下架。
- Google Play 商品 ID、Base Plan、Offer 和包名。
- 测试/正式环境。
- 渠道配置和最后同步状态。

购买记录页面：

- 按用户、内部购买号、商品、渠道、状态和时间查询。
- 展示初购、续费、退款、撤销、拒付的时间线。
- 展示当前订阅状态和权益有效期。
- 展示回调处理记录和失败原因。
- Purchase Token 一律脱敏。
- 允许有权限的管理员执行“从渠道重新同步”，该操作只能查询并同步真实状态，不能发起退款。

## 3. Google 登录

### 3.1 技术决策

本期不引入 Supabase Auth，使用现有 Google ID Token 流程：

```text
Flutter Google 登录
    ↓
获取 Google ID Token
    ↓
HTTPS 提交给 Java 服务端
    ↓
服务端验证 signature / aud / iss / exp
    ↓
用经验证的 sub 查找或创建本地用户
    ↓
执行现有风控、登录日志和资料补全
    ↓
签发系统自有 JWT
```

选择该方案的原因：

- 现有系统已经有自己的用户、身份、邮箱登录、游客、JWT、风控和登录日志。
- 只为 Google 登录引入 Supabase 会形成 Google Session、Supabase Session 和自有 JWT 并存的复杂状态。
- 现有 `GoogleSignInFacade`、`GoogleIdTokenVerifierService`、Google 身份表和资料补全流程可继续复用。

只有未来决定将邮箱登录、密码找回、Google/Apple 登录、Session 刷新、MFA 和用户封禁整体迁移时，才重新评估 Supabase Auth。

### 3.2 身份抽象

```text
ExternalIdentityVerifier
├── GoogleIdentityVerifier
└── AppleIdentityVerifier  // 未来
```

安全规则：

- 必须使用 Google API Client Library 在服务端校验 Token。
- 校验签名、`aud`、`iss`、`exp` 和必要的 `email_verified`。
- 使用 `sub` 作为 Google 身份的唯一键，不使用邮箱作为唯一身份。
- 不信任客户端单独上报的 Google 用户 ID、邮箱和昵称。
- 同一 Google `sub` 不得绑定多个本地用户。
- 游客绑定 Google 时必须保留原本的本地用户 ID、信件、好友关系和支付权益。
- Google 身份或邮箱已被其他正常账号占用时不静默合并，返回明确冲突。

## 4. FCM 消息推送

### 4.1 推送场景

#### 普通信件

1. `letter_matched_in_transit`：匹配成功、信件已创建并进入在途状态时，向收件人推送一次。
2. `letter_arrived`：信件到达时，向收件人再推送一次。

两个事件分别幂等，同一事件不能因匹配重试、任务重试或多实例并发而重复发送。

去重键：

```text
letter_matched:{letterId}:{recipientUserId}
letter_arrived:{letterId}:{recipientUserId}
```

推送文案示例：

```text
在途：一封信正在路上。
到达：一封信已经抵达，等你拆封。
```

通知中不显示信件正文，也不暴露不必要的发件人资料。

#### 其他保留场景

- 时光信到期。
- 收到笔友申请。
- 笔友申请通过。
- 信件或内容审核未通过。
- 重要账号安全通知。
- 必要的系统公告或强制升级。

#### 明确禁止的场景

- 购买成功。
- 自动续费成功。
- 扣款失败。
- 订阅取消、过期或撤销。
- 退款、拒付或权益收回。

### 4.2 可靠性设计

业务服务不直接调用 FCM。业务状态变更和通知 Outbox 在同一数据库事务内提交，再由统一定时任务投递。

建议数据结构：

#### `bu_push_endpoint`

- 用户、设备和 Firebase Installation ID/Token。
- 平台、App 版本、语言和时区。
- 通知权限状态。
- 最后上报时间、失效时间和失效原因。

现有 `bu_user_device.push_token` 可在迁移期兼容，长期建议将风控设备和推送终端解耦。

#### `bu_notification_outbox`

- 事件类型、接收用户和模板。
- Payload 和页面路由。
- 唯一去重键。
- 计划发送时间、状态、尝试次数和错误信息。

#### `bu_notification_delivery`

- Outbox 和目标设备。
- FCM Message ID。
- 发送结果、错误码和发送时间。

FCM 返回设备无效时，标记对应 Endpoint 失效，不继续无限重试。

### 4.3 客户端

- 处理 Android 13+ 通知权限。
- 处理前台、后台和进程结束状态。
- Token/FID 刷新后及时上报。
- 登录后绑定推送终端，退出时解除当前用户绑定。
- 点击在途推送进入在途详情；点击到达推送进入可拆封详情。
- 同一用户的多台活跃设备均可接收。

## 5. 统一定时任务入口

### 5.1 目录约定

```text
schedule/
├── ScheduledTaskEntrypoints.java
├── SchedulerProperties.java
└── job/
    ├── StandardLetterDeliveryJob.java
    ├── TimeLetterDeliveryJob.java
    ├── PostOfficeMatchJob.java
    ├── MailOutboxDispatchJob.java
    ├── NotificationOutboxJob.java
    ├── BillingEventRetryJob.java
    ├── BillingReconciliationJob.java
    └── PushEndpointCleanupJob.java
```

规则：

- 只有 `ScheduledTaskEntrypoints.java` 允许出现 `@Scheduled`。
- 入口类只负责触发、通用日志、指标、异常隔离和锁，不包含业务 SQL 或状态逻辑。
- 所有周期、批量大小、超时和开关集中在 `SchedulerProperties`。
- 使用 UTC 作为服务端计算和 cron 时区。
- 多实例部署必须使用分布式锁，防止同一任务并发重复执行。
- 任务以小批次、可重试、幂等的方式处理。
- 单个任务失败不得阻断其他任务。

可增加架构测试或 CI 检查，确保搜索 `@Scheduled` 时只命中统一入口类。

### 5.2 任务触发与推送关系

- `PostOfficeMatchJob` 匹配成功并创建在途信件时，在同一事务写入 `letter_matched_in_transit` Outbox。
- `StandardLetterDeliveryJob` 将信件改为已到达时，在同一事务写入 `letter_arrived` Outbox。
- `NotificationOutboxJob` 只负责发送已提交的通知。
- `BillingEventRetryJob` 重试处理失败的渠道事件。
- `BillingReconciliationJob` 只校准异常、临近边界或长时间未同步的记录，不全量高频轮询 Google API。

## 6. 配置与密钥

所有密钥只通过安全配置或环境变量提供，不提交到仓库：

- Google OAuth Web Client ID。
- Google Play Developer API 服务账号凭证。
- Google Cloud Pub/Sub 项目、Topic、Subscription 和 Push audience。
- Firebase Project ID 和 Admin SDK 凭证。
- Purchase Token 加密密钥。

测试和正式环境必须分离，本地 `test-override` 和模拟购买接口在生产环境必须关闭。

## 7. 验收标准

### 7.1 支付

- 伪造、过期、包名不符或商品不符的 Token 不发放权益。
- 同一 Token 不能绑定到不同用户。
- 重复客户端校验和重复 RTDN 不重复发权益、不重复记流水。
- `PENDING` 不授权，成功支付后立即授权。
- 续费正确延长订阅时间，并新增独立交易流水。
- 取消自动续期后，当前周期内仍有权益。
- 宽限期、暂停、扣款失败、过期和恢复均按渠道状态正确改变权益。
- 用户在 Google Play 发起退款后，即使 App 不在线，服务端也能通过渠道事件收回权益。
- 换设备或重装后可恢复有效购买。
- 管理后台无退款按钮，也无人工改支付状态能力。

### 7.2 Google 登录

- 真实 Google 账号可完成首次登录、资料补全和再次登录。
- 无效 Token、错误 audience 和过期 Token 均被拒绝。
- 相同 `sub` 始终映射到同一本地用户。
- 游客绑定 Google 后不丢失原账号业务数据。
- Google 身份或邮箱冲突时不静默合并用户。
- 登录成功后继续使用现有 JWT、设备风控和登录日志。

### 7.3 FCM

- 同一封信匹配成功后只发一次在途推送。
- 同一封信到达后只发一次到达推送。
- 在途和到达是两个独立事件，可各发一次。
- 支付、续费、退款、拒付和订阅变更不发送 FCM。
- 匹配、到达或推送任务重试不造成重复推送。
- 设备 Token/FID 刷新后可继续收到推送。
- 无效终端被自动停用，不无限重试。
- 通知栏不泄露信件正文或其他敏感信息。
- 点击两类信件推送均跳转到正确状态的页面。

### 7.4 定时任务

- 代码中只有 `ScheduledTaskEntrypoints.java` 包含 `@Scheduled`。
- 多实例运行时同一批数据不被重复处理。
- 任务错误有明确日志、指标和可重试状态。
- 一个任务失败不影响其他定时任务继续执行。

## 8. 建议实施顺序

1. 集中现有 `@Scheduled` 入口，建立通用任务包装、配置和分布式锁。
2. 完成 Google ID Token 生产配置、真机登录和账号绑定验收。
3. 新增支付通用表和 `BillingProvider` 抽象，迁移现有 VIP 订阅兼容逻辑。
4. 完成 Google Play 客户端购买、服务端真实校验、acknowledge 和恢复购买。
5. 接入 RTDN，完成续期、取消、宽限期、过期和用户渠道退款处理。
6. 扩展管理后台商品管理，增加只读购买记录。
7. 接入 FCM、通知 Outbox、多设备终端管理和 Deep Link。
8. 完成 Google Play 测试渠道、回调重放、多实例、异常恢复和全链路验收。
