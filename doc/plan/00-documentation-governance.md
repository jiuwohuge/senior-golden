## 2. 单篇文档必备元信息

每篇**主动维护**的 Markdown 须在**标题下首段**（或紧接标题的引用块）包含：

| 字段 | 说明 |
|------|------|
| **版本** | 语义化小版本，如 `1.0`、`1.1`；破坏性结构重排升 `x.0` |
| **更新** | `YYYY-MM-DD` |
| **维护人** | `AI + Owner` 或实名；多人协作可写 `Owner + 子系统` |

**版本 bump 规则**：

- 仅修正错别字、链接：可不升版本，只改「更新」日期。
- 与代码不一致的进度修正：小版本 **+0.1**。
- 章节结构重组、真源职责变更：**+1.0**。

## 3. 淘汰与归档机制

| 动作 | 条件 | 操作 |
|------|------|------|
| **标记归档** | 仍具历史价值但不随迭代更新 | 文首增加 `> **[归档]** 仅作参考；执行以 doc/plan/01、05 为准。` |
| **移出仓库** | 重复且已由其他文档完全替代 | PR 删除并在 `progress.md` 记一行删除原因 |
| **合并** | 两篇内容 80%+ 重叠 | 保留真源一篇，另一篇只留重定向段落 1 个月后删除 |

**当前归档声明**：[`doc/1、需求文档.md`](../1、需求文档.md) 为产品需求全文归档，**不替代** FP 清单。

---

## 4. 与代码对齐的工作流（消除进度不一致）

1. **改代码或接新 FP**：先改实现，再更新 **`01-feature-list.md`** 对应行，再更新 **`05-task-tracker.md`** 状态，再在 **`progress.md`** 写一行摘要。  
2. **叙事类文档**（`07`、`feature-overview`、`PLAN` 功能清单）：至少在有**对外演示 / 发版**前，按 `01` 做一次勾选或状态同步。  
3. **`07` §2「遗漏表」**：保留历史 ID；新增列 **「实现状态（日期）」** 或在 §2.0 维护对齐表，避免读者误以为「缺」仍为当前事实。  
4. **禁止**：仅在 `PLAN` 或口头结论中标记完成，而不更新 `01`/`05`。
